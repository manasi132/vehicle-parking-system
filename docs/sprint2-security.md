# Sprint 2 security verification

- Automated API coverage includes wrong-role 403 responses and production-configuration 429 throttling for authentication and reservation requests. The booking limiter is per process and per IP; shared or multi-instance deployments need a shared rate-limit store and trusted-proxy configuration.
- `npm audit --omit=dev` reported no production dependency vulnerabilities for backend or frontend in this local run. This does not cover development-only dependencies or replace a security assessment.
- **OWASP ZAP 2.17.0 passive baseline: completed locally.** The final report is saved as `docs/security/zap-baseline-local.json`. It contains one informational finding, “Modern Web Application,” and no high, medium or low findings. The initial local frontend preview lacked CSP, anti-clickjacking and content-type headers; preview and reverse-proxy configuration were updated and the passive scan rerun. A real Stripe Elements test-mode browser payment and refund subsequently passed through the preview CSP. The scan covered a disposable loopback frontend, public responses and selected authenticated API requests through ZAP, including admin success, wrong-role 403s, unauthenticated 401 and missing receipt 404. It was passive only: it did not run an authenticated spider, active attacks or test a deployed server. Fixture JWTs are redacted before saving the report.
- Reproduce the local passive scan after building the frontend with `ZAP_HOME` and `ZAP_DATA_DIR` pointing to a local ZAP 2.17.0 installation and add-ons, and `ZAP_JAVA` pointing to a compatible Java executable: `node backend/scripts/run-zap-baseline-local.cjs`. It starts disposable loopback services and does not use Stripe or shared credentials. The preview headers support a configured API origin; a separate deployed frontend host must configure equivalent headers, including the actual HTTPS API origin in CSP `connect-src`.
- The public availability stream exposes only lot ID, slot ID, status and timestamp; it does not broadcast reservation or vehicle details. Optional MongoDB change-stream fan-out is tested across two processes, but requires a replica set and is not transactional with the underlying slot write.
- Manasi's OTP relay contract is incorporated into the shared adapter, but the provider must be configured and PR #40 coordinated. Notification delivery retries are at-least-once and require an idempotent downstream provider; booking events have a durable reservation marker, but entry, exit and payment event enqueue is not transactional with domain writes.
- **Admin audit consistency: failed a fault-injection check.** When `AuditLog.create` was forced to fail on a disposable database, an admin lot-create returned HTTP 500 after the lot was already persisted, with no audit entry. The current middleware is not atomic with the underlying write. Resolving this requires a reviewed replica-set transaction or equivalent durable design covering admin and gate operations; it is not safe to claim completion from successful-path tests alone.
- **Booking lease-loss fencing: failed a fault-injection check.** A disposable test simulated a successor taking ownership, waited for the original worker's heartbeat to detect loss, and then let the original callback write. The reservation was persisted before `SLOT_LOCK_LOST` was returned. Ordinary concurrent requests pass, but the current post-callback check cannot prevent stale-worker writes. A reviewed transactional or otherwise fenced design is required before claiming crash-safe booking.
